# 开发文档 01：后端接口与数据模型设计

> 适用范围：用户端（user）、客服工作台（agent/admin）、管理端扩展、实时事件流
> 基线：现有 FastAPI + SQLAlchemy(async) + Alembic + PostgreSQL + pgvector
> 约定：统一响应包 `{code, message, data}`；错误码沿用现有体系（40000 参数、40300 无权限、40400 不存在、40900 冲突）；时间统一 UTC ISO8601。

## 1. 角色与权限扩展

### 1.1 角色

`app/models/user.py`：

- `Role` 枚举增加 `USER = "user"`；
- `users` 表 `ck_users_role` 约束增加 `'user'`；
- `schemas/auth.py` 的 `UserOut.role`、`UserCreate.role` 自动继承（枚举类型）。

### 1.2 权限依赖

- 公开：注册；
- `user`：用户端接口（/api/user/*）、事件流 scope=user；
- `agent/admin`：客服工作台接口（/api/agent/*）；
- `admin`：管理端看板、渠道配置、用户管理（现有）；
- 现有管理端接口（/api/chat、/api/sessions 等）权限保持不变，**不得对 user 开放**。

## 2. 认证接口

### 2.1 新增 `POST /api/auth/register`（公开）

请求：

```json
{
  "username": "zhangsan",
  "password": "abc12345",
  "confirm_password": "abc12345",
  "display_name": "张三",
  "captcha": "8"
}
```

校验：

- username：4~32，字母/数字/下划线/中文，唯一；
- password：8~64，至少含字母和数字；confirm 一致；
- captcha：算术验证码（后端 session/内存 + 短过期），可先做“注册防刷限流 + 验证码”；
- 默认 `role=user`、`status=active`。

响应：直接返回 `TokenPair` + `user`（自动登录）：

```json
{ "code": 0, "data": { "access_token": "...", "refresh_token": "...", "user": { "id": "...", "username": "zhangsan", "display_name": "张三", "role": "user", "status": "active" } } }
```

限流：按 IP 每分钟 ≤ 5 次（`enforce_register_rate_limit`，复用 `core/ratelimit.py` 模式）。

### 2.2 新增 `PUT /api/auth/password`（登录用户）

请求：`{ "old_password": "...", "new_password": "..." }`

逻辑：校验旧密码 → 更新哈希 → `token_version + 1` → 返回 `{ "message": "密码已修改，请重新登录" }`（前端收到后清 token 跳登录）。

### 2.3 复用

- `POST /api/auth/login`、`POST /api/auth/refresh`、`GET /api/auth/me`：不变，`user` 角色同样可登录；
- 登录失败锁定：users 表新增 `failed_login_count`、`locked_until`（迁移见 §6），连续 5 次失败锁 15 分钟（在 `auth_service.authenticate_user` 中实现）。

## 3. 用户端接口（/api/user/*）

权限：`require_roles(Role.USER)`。所有查询强制 `WHERE session.user_id == current_user.id` / 工单归属校验，越权返回 40300。

### 3.1 对话 `POST /api/user/chat`（SSE）

请求：

```json
{ "session_id": null, "message": "钟点工和包月保洁有什么区别？" }
```

- `session_id` 为空则创建新会话：`channel="web_user"`，`kb_ids` 由后端按渠道配置解析（见 §4），`user_id=当前用户`；
- `session_id` 非空必须属于当前用户，否则 40300；
- 忽略任何 `kb_ids/model_profile_id/form_data` 字段（用户端不允许指定）；
- 其余复用现有 chat 流水线（意图分类 → 检索 → LLM），事件协议与现有 `/api/chat` 一致：`message_start / token / citations / done / error`；
- `citations` 事件对 user 仅返回 `{ document_name, question }`（脱敏）；
- 转人工会话（status=transferred）继续走现有“仅入库、AI 不回复”逻辑。

### 3.2 我的会话

`GET /api/user/sessions?page=1&page_size=10`

返回列表项：`{ id, status, updated_at, message_count, last_message, ticket_no }`。

`GET /api/user/sessions/{id}`

返回：`{ session: {id, status, channel, created_at, updated_at}, messages: [{id, role, content, created_at}] }`。

- messages 只含 `user/assistant/agent/system` 的 id/role/content/created_at；
- 不含 intent、cited_chunk_ids、citations、trace；
- 归属校验：`session.user_id == current_user.id`。

### 3.3 我的工单

`GET /api/user/tickets?status=open|processing|closed&page=1&page_size=10`

列表项：`{ id, ticket_no, status, priority, session_id, created_at, updated_at }`。

`GET /api/user/tickets/{id}`

返回：工单信息 + 会话完整消息（同上脱敏）+ `rating: {score, comment} | null` + `can_rate: bool`（closed 且未评价）。

`POST /api/user/tickets/{id}/rating`（P2，可留接口）

请求：`{ "score": 5, "comment": "很好" }`；score 1~5；ticket 必须 closed 且属于当前用户；唯一评价。

## 4. 渠道与默认知识库

新增表 `channel_configs`：

| 列 | 类型 | 说明 |
|---|---|---|
| channel | varchar(50) PK | 如 `web_user` |
| default_kb_ids | jsonb | 默认知识库列表 |
| allow_human | bool default true | 是否允许转人工 |
| business_hours | jsonb null | 营业时间（二期用） |
| updated_at | timestamptz | |

- 会话创建时：`kb_ids = channel_configs.default_kb_ids`（未配置则报 40000“渠道未配置默认知识库”）；
- 管理端接口：`GET/PUT /api/settings/channel`（admin）读写 `web_user` 配置；
- 检索沿用 `filter_accessible_kb_ids`（user 可见性按 KB `visibility` 规则）。

## 5. 客服工作台接口（/api/agent/*）

权限：`require_roles(Role.AGENT, Role.ADMIN)`。

### 5.1 工单队列 `GET /api/agent/tickets`

参数：`status=open|processing|closed|all`、`mine=true`（只看自己负责）、`page/page_size`。

列表项：`{ id, ticket_no, status, priority, user_id, user_name, session_id, unread_count, last_message, last_message_at, claimed_at, closed_at }`。

排序：`open` 按优先级 + 创建时间；`processing` 按认领时间。

### 5.2 认领 `POST /api/agent/tickets/{id}/claim`

原子更新：

```sql
UPDATE tickets
SET assignee_id = :me, status = 'processing', claimed_at = now()
WHERE id = :id AND status = 'open'
```

- rowcount=1 → 返回工单详情；rowcount=0 → `40900` “该工单已被其他客服认领”；
- 成功后发布 `ticket.claimed` 事件。

### 5.3 工单详情 `GET /api/agent/tickets/{id}`

返回：工单完整信息 + 会话消息（内部字段完整：intent/citations 等）+ 用户资料（username/display_name）+ rating。

权限：admin 或 `assignee_id == 当前用户`（未认领时 admin/agent 均可看，用于认领前预览——可只读）。

### 5.4 回复 `POST /api/agent/tickets/{id}/reply`

请求：`{ "content": "..." }`（1~2000 字）

逻辑：

- 权限：assignee 或 admin；工单非 closed；
- 写入 `messages(role='agent', session_id=工单.session_id)`；
- 发布 `message.new` 事件（scope=user 该会话用户 + scope=agent 该 assignee）；
- 返回消息对象。

### 5.5 关闭 `POST /api/agent/tickets/{id}/close`

请求：`{ "reason": "已解决" }`（必填，≤200）

逻辑：权限同回复；`status='closed'`、`closed_at=now()`、`close_reason=reason`；发布 `ticket.closed`。

### 5.6 在线状态 `PUT /api/agent/status`

请求：`{ "online": true }`；存入内存/Redis（key=`agent:online:{user_id}`，TTL 可刷新）；`GET /api/agent/status` 返回当前状态。一期可简化为前端本地状态 + 用户端不依赖。

### 5.7 已读游标 `POST /api/agent/sessions/{session_id}/read`

请求：`{ "last_read_message_id": "..." }`；更新 `session_reads`（reader_role='agent'）。

用户端对应：`POST /api/user/sessions/{session_id}/read`（reader_role='user'）。

## 6. 管理端接口扩展

### 6.1 工单看板 `GET /api/admin/tickets/overview`（admin）

返回：

```json

  "total": 120, "open": 8, "processing": 5, "closed_today": 23,
  "stale_open": [ { "ticket_no": "TK...", "created_at": "...", "minutes": 35 } ]
```

`stale_open` = open 超过 30 分钟未认领。

### 6.2 渠道配置 `GET/PUT /api/settings/channel`（admin）

### 6.3 用户管理

## 7. 事件流（SSE）

### 7.1 订阅端点

`GET /api/stream/events?scope=user|agent|admin`

- 登录态必填；SSE 响应头 `Content-Type: text/event-stream`；
- 每 20s 发送 `: ping` 心跳；
- 断线重连由浏览器 EventSource 自动处理，重连后前端全量重拉列表（事件仅作增量提示）。

### 7.2 事件帧

```text
event: ticket.created
data: {"event_id":"uuid","ticket_id":"uuid","ticket_no":"TK...","session_id":"uuid","status":"open","priority":"medium","user_id":"uuid","created_at":"..."}
```

事件类型与 payload：

| 事件 | payload 关键字段 |
|---|---|
| ticket.created | ticket_id, ticket_no, session_id, priority, user_id, created_at |
| ticket.claimed | ticket_id, assignee_id, claimed_at |
| ticket.closed | ticket_id, closed_at, reason |
| ticket.updated | ticket_id, status, priority, updated_at |
| message.new | message_id, session_id, ticket_id?, role, created_at, from_user/from_agent |

### 7.3 权限过滤

- `scope=user`：仅 `session.user_id == 当前用户` 的事件（ticket 关联 session 归属）；
- `scope=agent`：open 工单事件 + `assignee_id == 当前用户` 的事件；
- `scope=admin`：全部；
- 过滤必须在服务端完成，前端不可信。

### 7.4 实现建议

- 一期：进程内 `EventBus`（asyncio.Queue per subscriber + 订阅条件函数）；
- 预留 `RedisPubSub` 实现（key=`cs:events`，JSON 序列化），多实例部署时切换；
- 订阅管理：`app/services/event_service.py`：`subscribe(scope, user_id, queue)` / `publish(event)` / `heartbeat` 任务。

## 8. 数据模型变更（Alembic 迁移）

### 8.1 users

```text
ALTER TABLE users DROP CONSTRAINT ck_users_role;
ALTER TABLE users ADD CONSTRAINT ck_users_role CHECK (role IN ('admin','agent','viewer','user'));
ALTER TABLE users ADD COLUMN failed_login_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE users ADD COLUMN locked_until TIMESTAMPTZ;
```

### 8.2 messages

```text
ALTER TABLE messages DROP CONSTRAINT ck_messages_role;
ALTER TABLE messages ADD CONSTRAINT ck_messages_role CHECK (role IN ('user','assistant','agent','system'));
```

### 8.3 tickets

```text
ALTER TABLE tickets ADD COLUMN claimed_at TIMESTAMPTZ;
ALTER TABLE tickets ADD COLUMN closed_at TIMESTAMPTZ;
ALTER TABLE tickets ADD COLUMN close_reason VARCHAR(200);
```

### 8.4 新表 session_reads

```text
id UUID PK
session_id UUID FK sessions ON DELETE CASCADE
reader_role VARCHAR(20)  -- user / agent
reader_id UUID FK users ON DELETE CASCADE
last_read_message_id UUID FK messages ON DELETE CASCADE
updated_at TIMESTAMPTZ
UNIQUE (session_id, reader_role, reader_id)
```

### 8.5 新表 ticket_ratings

```text
id UUID PK
ticket_id UUID FK tickets ON DELETE CASCADE UNIQUE
user_id UUID FK users ON DELETE CASCADE
score SMALLINT CHECK (score BETWEEN 1 AND 5)
comment VARCHAR(500)
created_at TIMESTAMPTZ
```

### 8.6 新表 channel_configs

```text
channel VARCHAR(50) PK
default_kb_ids JSONB NOT NULL DEFAULT '[]'
allow_human BOOLEAN NOT NULL DEFAULT TRUE
business_hours JSONB
updated_at TIMESTAMPTZ
```

迁移命名：`0006_user_side.py`（可拆 `0006_role_user.py` / `0007_agent_messages.py` / `0008_workbench.py`）。

## 9. 关键实现要点

1. **行级权限**：会话详情、工单详情、读取游标、评价、事件订阅全部按归属过滤；写一个 `require_own_session/user` 辅助函数，避免漏检；
2. **认领原子性**：单条条件 UPDATE，禁止“先 SELECT 再 UPDATE”；
3. **用户端 chat 复用**：`/api/user/chat` 与现有流水线共用 `_run_chat_pipeline` 逻辑，仅入口参数与输出脱敏不同（建议抽取公共函数）；
4. **消息脱敏**：用户端响应模型单独定义（`UserMessageOut`），不复用 `MessageOut`；
5. **事件幂等**：事件带 `event_id`，前端去重；后端发布时保证“先落库后发事件”，避免事件先于数据可见；
6. **密码策略**：注册/改密统一走 `core/security.py` 校验函数；
7. **测试**：新增 `tests/test_user_side.py`、`tests/test_agent_workbench.py`，见开发文档 03。

## 10. 变更记录（实施后追加）

### 10.1 新增接口

- `POST /api/agent/tickets/{id}/release`（assignee/admin）：processing → open，清空 assignee/claimed_at，写 ticket_notes（"释放工单：原因"），发布 `ticket.updated` 事件。
- `POST /api/auth/captcha`：算术验证码获取（注册防刷配套）。

### 10.2 权限与职责分离

- 工单写操作（claim/reply/close/release、在线状态、已读游标、旧 `/api/tickets/{id}/action`）默认仅 agent；admin 仅当 `ALLOW_ADMIN_TICKET_OPS=true`（`core/config.py`）。
- 工单读操作（`/api/agent/tickets` 列表/详情、`/api/tickets` 列表/详情）admin/agent 可读；列表按查看权限过滤（非 admin 仅 open 全部 + 自己负责的 processing/closed）。
- viewer 收敛：`/api/sessions`、`/api/tickets`（列表/详情）对 viewer 403，仅保留 dashboard 只读。
- 会话标注：`eval_set_id` 仅 admin 可指定；agent 标注仅产生候选（pending）。
- 工单写操作统一写 `audit_logs`（ticket_claim/reply/close/release）。

### 10.3 模型与迁移

- 迁移 `0010_user_side_workbench`：users 角色加 user + failed_login_count/locked_until；messages 角色加 agent；tickets 加 claimed_at/closed_at/close_reason；新表 session_reads / ticket_ratings / channel_configs。
- 迁移 `0011_workbench_indexes`：ix_sessions_user_id、ix_tickets_user_id、ix_tickets_assignee_id。

### 10.4 事件与可观测

- 事件总线接入 Redis pub/sub 中继（instance_id 防回环、故障降级本地）；事件类型与 §7.2 一致。
- SSE 连接指标 `sse_connections_active` / `sse_connections_total` 与连接上限 `sse_max_connections`（默认 1000，超限 429）。
- 队列/详情性能：未读数批量 SQL 聚合、last_message `DISTINCT ON`、详情引用一次反查（消除 N+1）。
