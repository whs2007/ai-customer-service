# 05 项目审计报告

> 审计对象：AI 智能客服系统「用户端 + 客服工作台 + 三端实时联动」（P0+P1，P2 预留）
> 审计方式：只读代码审查 + 自动化测试 + 本地 HTTP 实测 + 数据库实证
> 审计日期：2026-08-16
> 依据文档：需求文档 11/12/13、开发文档 01/02/03

---

## 1. 执行摘要

总体结论：**P0+P1 主体实现与设计文档契约基本一致，安全红线（行级权限、脱敏、认领原子性、密钥隔离）落实到位，后端 113 个测试全量通过、前端 tsc 通过**。未发现可被直接利用的越权/数据泄露漏洞。

但存在 **2 个高优先级功能缺陷**，直接影响"三端实时联动"这一核心交付：

1. **用户端 SSE 事件流 Token 选择错误**（`eventStream.ts:29`）：`/api/stream/events?scope=user` 不匹配 `url.includes('/user/')` 判断，用户端实时事件连接恒 401、每 2 秒空转重连，人工回复/工单状态无法实时到达用户端。
2. **转人工后用户继续留言不发布 `message.new` 事件**（`chat_pipeline.py:145-160`）：消息正常入库但客服端收不到实时推送，违反 12 §3.3 与 13 §4 的明确要求。

次要风险集中在**数据量增长后的性能**（队列接口 N+1、关键列缺索引、embedding 无缓存）与**并发原子性**（注册同名竞态、已读游标 upsert 竞态）。事件总线 Redis pub/sub 仅预留未接线，多实例部署时跨实例事件会丢失（当前单实例部署不受影响）。

最大风险点：**用户端实时链路（H1）**——它是"三端实时联动"的验收核心，且缺陷位于前端静态判断，属于上线前必须修复项。

## 2. 问题清单

### 2.1 严重（Critical / P0）

无。未发现认证绕过、越权读取、密钥泄露、可直接利用的注入漏洞。

### 2.2 高（High / P1）

#### H1 用户端 SSE 事件流 Token 选择错误，实时联动失效

- 位置：`frontend/src/utils/eventStream.ts:29`
- 问题：`const token = url.includes('/user/') ? getUserAccessToken() : getAccessToken();`。用户端调用 URL 为 `/api/stream/events?scope=user`（`pages/user/UserChatPage.tsx:80`、`pages/user/UserTicketsPage.tsx:34`），该字符串**不包含** `"/user/"` 子串，因此误用管理端 token key → 对 user 角色恒为 401 → `onError` 后每 2 秒重连（`eventStream.ts:89-91`），永不恢复。
- 为什么是问题：用户端"人工回复实时到达、工单状态实时变化"（12 §7.5、13 §5.2）完全依赖此连接；workbench（scope=agent）与看板（scope=admin）走管理端 key 正确，唯用户端失效。
- 验证：用户登录 `/user/chat` 后浏览器 Network 面板可见 `GET /api/stream/events?scope=user` 返回 401，并持续重连。
- 修复建议：`connectEventStream` 增加显式 `token` 参数（由调用方传入），或按 `scope=user` 判断；为 eventStream 补一条前端单测（当前无测试覆盖）。
- 优先级：P1

#### H2 转人工后用户继续留言不发布 `message.new`

- 位置：`backend/app/services/chat_pipeline.py:145-160`
- 问题：会话 `status=transferred` 时，阶段 1 已把用户消息落库（111-114），但该分支直接 `return`，未发布 `message.new`；事件发布逻辑集中在阶段 3（259-300），转人工后的留言永远不触发。
- 为什么是问题：12 §3.3 明确"转人工后……新消息仅入库（role=user），并推送给客服端"；13 §4 事件表 `message.new` 覆盖"用户/AI/人工发消息"。当前客服端只能靠手动刷新/打开工单看到新留言，实时体验断裂。
- 验证：转人工后以用户身份再发一条消息，观察无任何 SSE 事件产生（客服端队列未读不变化）。
- 修复建议：transferred 分支在 `return` 前查询该会话工单，发布 `message.new`（携带 session_id、user_id、ticket_status、assignee_id、role=user）。
- 优先级：P1

#### H3 客服队列/详情接口 N+1 与全量消息拉取

- 位置：`backend/app/services/ticket_service.py:335-339`（每工单一次 `get_unread_count`）、`:327-331`（`last_map` 按 session_id 集合拉取**全部**消息行）、`:420-430`（详情逐条 assistant 消息反查 citations）
- 问题：队列页 100 条工单 → 至少 101 次查询；last_map 对每个会话把整张 messages 读进内存再取第一条；详情页引用多时逐条查 chunks。
- 为什么是问题：工单数/会话消息量上涨后队列接口延迟线性恶化；`get_unread_count` 本身又是 2-3 次查询（游标+计数）。
- 验证：`EXPLAIN` 可复现；或对 100 工单页打点统计查询次数。
- 修复建议：未读数改为批量 LEFT JOIN 游标后按 `(session_id, role)` 聚合计数；last_message 用 `DISTINCT ON (session_id)` 或 LATERAL；详情页按消息集合一次性反查 citations 再映射。
- 优先级：P1（性能）

### 2.3 中（Medium / P2）

#### M1 新查询缺少关键索引

- 位置：数据库实证（`pg_indexes`）：`sessions.user_id`、`tickets.user_id`、`tickets.assignee_id` 均无索引；tickets 已有 `ix_tickets_status_priority_created` 与 `ix_tickets_ticket_no`。
- 问题：`list_my_sessions`（WHERE user_id）、`list_my_tickets`（WHERE user_id）、`list_agent_tickets?mine=true`（WHERE assignee_id）在万级数据下全表扫描。
- 修复建议：新增迁移 `ix_sessions_user_id`、`ix_tickets_user_id`、`ix_tickets_assignee_id`。
- 优先级：P2

#### M2 用户端流式对话中切换会话存在竞态

- 位置：`frontend/src/pages/user/UserChatPage.tsx:167-180`
- 问题：`sendMessage` 的 finally 中 `const sid = sessionId` 捕获的是流结束时组件当前状态；若流式期间用户点击了其它会话，`loadSession` 已切换 `sessionId`，旧流结束后会用**旧会话**数据覆盖当前视图消息。
- 为什么是问题：开发文档 02 §7 明确要求"流式渲染边界（streaming 中重复发送/快速切会话）"稳健；当前会串台。
- 修复建议：拉取前校验 `sid === 当前 sessionId` 再 setMessages；切换会话时 abort 进行中的流。
- 优先级：P2

#### M3 注册用户名唯一性竞态可致 500

- 位置：`backend/app/services/auth_service.py:141-152`；同模式存在于 `user_service.create_user`（admin 建号）
- 问题：先 SELECT 判重再 INSERT，两个并发请求同名时后提交方触发唯一约束 `IntegrityError`，未捕获 → 500 而非 40900。
- 为什么是问题：注册防刷场景正是并发高发场景，错误码契约（40900 冲突）应保持一致。
- 修复建议：捕获 `IntegrityError` 转 `ConflictError("用户名已存在")`，或 `INSERT ... ON CONFLICT DO NOTHING` 后复核。
- 优先级：P2

#### M4 已读游标 upsert 非原子

- 位置：`backend/app/services/read_service.py:37-53`
- 问题：select 后 insert/update；同一 reader 并发提交 read 时可能命中 `uq_session_read_reader` 唯一约束 → 500。
- 修复建议：`INSERT ... ON CONFLICT (session_id, reader_role, reader_id) DO UPDATE`。
- 优先级：P2

#### M5 agent 已读接口缺少归属校验

- 位置：`backend/app/api/routes/agent.py:134-144`
- 问题：任意 agent/admin 可对任意 `session_id` 写已读游标，未校验会话/工单归属（仅写入游标，无数据读取，不构成泄露）。
- 修复建议：校验 session 关联工单为 open 或 assignee/admin（复用 `get_agent_ticket_detail` 权限逻辑）。
- 优先级：P2

#### M6 算术验证码内存存储无清理、可被程序化求解

- 位置：`backend/app/core/ratelimit.py:85-116`
- 问题：`_captcha_store` 只增不减（过期项仅在相同 challenge_id 被再次校验时清除），高频调用会持续占用内存；算术验证码可被脚本秒解。
- 说明：MVP 已声明算术验证码为最快方案，真正防线是注册限流（5 次/IP/分钟，`ratelimit.py:81`），因此不构成绕过。
- 修复建议：定期清理过期项或迁移 Redis（带 TTL）；后续接短信/图形验证码。
- 优先级：P2

#### M7 chat 流水线异常分支可能透出内部 message

- 位置：`backend/app/services/chat_pipeline.py:315-319`
- 问题：`message = getattr(exc, "message", "服务内部错误，请稍后重试")`——非 AppError 但带 `.message` 属性的第三方异常可能把内部文本写入 SSE error 帧。
- 修复建议：仅 `AppError` 透出 code/message，其余统一 50000 + 友好文案（与 `main.py:185-191` 的兜底一致）。
- 优先级：P2（安全加固）

#### M8 前端 eslint 2 个错误

- 位置：`frontend/src/pages/user/UserChatPage.tsx:121-122`（`react-hooks/purity`：事件处理器中调用 `Date.now()` 被规则误报为渲染期不纯）
- 影响：`npm run lint` 失败，CI 会被卡；运行期无实际 bug。
- 修复建议：改用自增 ref 或 `crypto.randomUUID()` 生成临时消息 id。
- 优先级：P2

#### M9 Embedding 每次检索都调 API，无缓存

- 位置：`backend/app/rag/embeddings.py`（`embed_texts` 直接 `_embed_via_api`）
- 问题：每轮检索 1 次向量化调用；对话量大时成本与检索 P95 受网络影响。
- 修复建议：按文本 hash 做短时 LRU（如 10 分钟 / 512 条）；或对高频问题做答案缓存。
- 优先级：P2

#### M10 事件总线 Redis pub/sub 未接线（多实例限制）

- 位置：`backend/app/services/event_service.py:41`（`_redis_pubsub = None`）、`:51-70`（publish 仅进程内投递）
- 问题：文档 11 §9.3 / 开发文档 01 §7.4 声明"多实例部署时切换 Redis pub/sub（接口不变）"，但当前 publish 路径完全没有 Redis 写入；多实例时跨实例订阅者收不到事件。单实例部署不受影响。
- 修复建议：实现 Redis 发布通道（PUBLISH `cs:events`）+ 订阅端 listen 后复用 `_scope_allows` 过滤；或在部署文档中明确"事件流仅支持单实例"。
- 优先级：P2（若计划多实例则升 P1）

## 6. 举一反三

### 6.1 模式推广核查结果

- **越权模式**：逐个核对所有按 ID 查询的接口——用户端会话/工单/评价/已读/chat session_id 均有归属校验（HTTP 实测 403）；客服端工单详情有权限校验（admin/assignee/open 可读）；**唯一遗漏**为 agent 已读游标（M5，无信息泄露）。
- **脱敏模式**：全量搜索用户端响应模型与 SSE 事件——会话/工单详情仅 id/role/content/created_at；chat citations 仅 document_name/question；事件 payload 仅含 uuid 型 user_id/assignee_id，无 intent/cited/trace。管理端内部字段（intent/cited_chunk_ids/citations）仅在 agent/admin 接口返回。
- **并发模式**：认领已用原子条件更新并有并发测试；注册与已读游标仍为 check-then-act（M3/M4），同模式需统一改原子操作。

### 6.2 系统性风险（未来规模下的先爆点）

| 规模信号 | 先爆点 | 触发阈值（估算） | 应对 |
|---|---|---|---|
| 用户同时在线 | 用户端 SSE 连接数（当前无上限/无指标） | 数千连接 | 连接数指标 + 网关层 SSE 卸载/限流 |
| 工单量 | 队列接口 N+1 + 缺 assignee/user 索引 | 1 万工单 | H3 + M1 修复 |
| 会话消息量 | last_map 全量拉取 | 单会话数千消息 | DISTINCT ON/LATERAL |
| 对话日活 | embedding 调用成本 | 日对话数千轮 | M9 缓存 |
| 多实例部署 | 事件跨实例丢失 | 第 2 个实例上线 | M10 接线 Redis pub/sub |
| 断线风暴 | 固定 2s 重连放大 | 网关/后端抖动时 | L5 退避抖动 |

### 6.3 对未来功能的铺垫

- **满意度报表**：`ticket_ratings` 已具备 ticket 唯一约束与 score 字段；报表需补 `created_at` 索引即可聚合。
- **工单超时提醒**：`tickets.status + created_at` 复合索引已可支撑 `>30min open` 查询，看板 `stale_open` 已实现；告警需接事件/定时任务。
- **分配策略/转派**：`assignee_id` 已存在，转派需扩展事件类型（如 `ticket.assigned`）与接口；无阻碍。
- **小程序端**：用户端接口为 REST+SSE；小程序无原生 EventSource，需自行解析 SSE 或预留 WebSocket 适配层（当前 SSE 协议可平滑包装）。
