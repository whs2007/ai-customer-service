【第三步：审计维度（逐项给证据）】

1. 功能完整性（对照需求文档 00–13 逐模块核对）
   - 每个模块/需求项 → 实现状态（已实现/部分/缺失/与文档不一致）→ 代码与接口证据；
   - 全项目功能是否串联完整：注册→对话→RAG→转人工→工单→客服回复→评价→统计→评测，链路是否有断点；
   - 用户端/客服端/管理端三端之间的数据一致性（状态、消息、未读、事件）。

2. 实际运行 Bug 与可靠性
   - 真实复现的 bug：步骤、现象、根因（代码位置）、影响、修复建议；
   - 并发/事务/幂等：抢单、重复提交、断线重发、事件重复、缓存一致性；
   - 异常降级：LLM/Embedding/Redis/DB 故障时系统行为是否符合预期、是否泄露内部信息；
   - 重试与超时：HTTP 超时、SSE 心跳、任务队列（inline/celery）失败重试。

3. 安全审计
   - 认证授权：JWT、token_version、角色、注册/登录/改密风控、限流；
   - 行级权限：所有按 ID 查询接口的归属校验（会话/工单/评价/事件订阅），越权横向测试；
   - 数据脱敏：用户端响应/SSE 是否泄漏 intent/cited_chunk_ids/trace 等内部字段；
   - 密钥与日志：.env/gitignore、API Key 是否泄漏、日志是否脱敏、异常是否回显堆栈；
   - 注入与 XSS、CORS、上传校验（扩展名/嗅探/恶意文件）、Prompt 注入防护有效性。

4. 性能与成本
   - 检索链路：embedding 调用频率与缓存、检索超时、RAG 全链路延迟实测（p95）；
   - LLM：并发、token 成本估算、流式体验；
   - 数据库：慢查询、N+1、索引覆盖、分页、未读计数在数据量增长下的表现；
   - 前端：首屏体积、构建时间、接口重复请求；
   - 规模推演：千级/万级用户、并发对话、SSE 连接数上限、多实例扩展点。

5. 架构与技术评估
   - 分层与模块边界（api/service/model/pipeline/rag/agents）是否清晰；
   - Agent 链路（意图分类→检索→重排→生成→兜底→转人工）设计的合理性、可解释性、可评测性；
   - 事件总线/SSE 方案在多实例下的正确性；会话与知识库权限模型；
   - 可观测性：日志、指标（Prometheus）、审计、链路追踪是否够用；
   - 部署：docker-compose、CI、迁移流程、配置管理、环境隔离。

6. 工程质量
   - 测试：全量 pytest 与前端 tsc 结果；覆盖率；关键用例（并发/越权/脱敏/转人工闭环）是否真实断言；
   - 代码质量：类型检查、lint、重复代码、死代码、命名、错误处理一致性；
   - 文档与实现一致性：需求文档/开发文档/实际代码是否对得上；
   - git 历史与 CI 是否规范。

【第四步：举一反三】
1. 模式推广：一个模块发现的问题，系统性检查其它模块是否存在同类问题；
2. 系统性风险与瓶颈：从现状推断规模上来后最先爆的点，给出阈值、预警与应对；
3. 改进路线图：按 P0（必须修）/P1（建议修）/P2（增强）输出，含预期收益、成本、风险、实施顺序；
4. 对未来需求的铺垫评估：多端（小程序）、多租户、工单分配策略、满意度报表、实时坐席、模型评测增强等。

【第五步：产出「简历可用素材」——这是本报告的核心增值】

## 使用建议

1. 项目实现并联调通过后运行本提示词；
2. 如果想控制耗时，可先跑“功能完整性 + 端到端实测 + 安全”，再跑性能与工程质量；
3. 报告产出后，重点使用第 11~13 节（亮点/弱点/简历素材/投递建议）来准备面试；
4. 建议审计报告与设计文档一起放入项目，作为“从需求到落地到复盘”的完整作品集证据。
